# TDD & Tidy First 워크플로우

## TDD (Test-Driven Development)

### Red-Green-Refactor 사이클

```
[Red] 실패하는 테스트 작성
  ↓
[Green] 테스트를 통과하는 최소한의 코드 구현
  ↓
[Refactor] 테스트 통과 상태에서 구조 개선
  ↓
  기능 완성까지 반복
```

### Red: 실패하는 테스트 작성

- 구현 전에 테스트를 **먼저** 작성한다
- 테스트 이름은 행위를 설명한다 (예: `shouldReturnPostWhenValidId`)
- 비즈니스 로직 변경 시 반드시 E2E 테스트도 추가한다
- 테스트 도구: Playwright (E2E)
- 하나의 테스트에 하나의 행위만 검증한다

### Green: 최소한의 코드 구현

- 테스트를 통과하기 위한 **최소한의** 코드만 작성한다
- 과도한 추상화나 미래 대비 코드를 작성하지 않는다
- "나중에 필요할 것 같다"는 코드를 추가하지 않는다
- 중복이 있어도 일단 통과시킨다 (리팩터링 단계에서 제거)

### Refactor: 구조 개선

- 테스트가 **모두 통과하는 상태**에서만 리팩터링한다
- 중복 제거, 네이밍 개선, 구조 정리를 수행한다
- 리팩터링 후 모든 테스트가 통과하는지 확인한다
- 리팩터링은 동작을 변경하지 않는다

## Tidy First

### 원칙: 구조적 변경과 행위적 변경을 분리한다

| 종류 | 커밋 타입 | 설명 | 예시 |
|------|-----------|------|------|
| 구조적 변경 | `refactor` | 동작 변경 없이 코드 구조만 개선 | 이름 변경, 메서드 추출, 파일 분리 |
| 행위적 변경 | `feat`/`fix` | 실제 기능 추가나 버그 수정 | 새 API, 버그 패치, UI 기능 |

### 적용 순서

1. 구조적 변경이 필요하면 **행위적 변경 전에 먼저** 수행한다
2. 구조적 변경을 별도 커밋으로 완료한다
3. 그 다음 행위적 변경을 수행하고 별도 커밋한다
4. **두 종류의 변경을 같은 커밋에 섞지 않는다**

### Tidy First 판단 기준

```
코드 변경이 필요할 때:
  ├── 기존 코드 구조가 변경을 어렵게 만드는가?
  │   ├── Yes → 먼저 구조 정리 (refactor 커밋) → 그 다음 기능 구현 (feat 커밋)
  │   └── No  → 바로 기능 구현 (feat 커밋)
  └── 구조 정리만 필요한가?
      └── Yes → refactor 커밋만 수행
```

## 버그 수정 시 TDD 절차

1. **버그를 재현하는 실패 테스트**를 먼저 작성한다
2. 테스트가 통과하도록 **최소한의 수정**을 한다
3. 리팩터링 후 **모든 테스트가 통과**하는지 확인한다

## 사소한 변경(minor change) 예외

다음에 해당하면 TDD 사이클(Red-Green-Refactor)을 생략할 수 있다:

- 비즈니스 로직 변경이 없는 경우
- 외부 API 계약(요청/응답/에러 코드) 변경이 없는 경우
- 토큰/인증/보안 정책 변경이 없는 경우
- 동작 결과가 동일한 리팩터링, 네이밍 수정, 주석/문구 수정
- UI 표시 텍스트, 로그 메시지, 코드 포맷 수정
